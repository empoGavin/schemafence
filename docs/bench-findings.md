# 基准测试结论

这份文件是手写的，`scripts/bench_report.py` 不会覆盖它——报表每次重跑都会变，
解读不会。数字全部来自 `docs/bench-report.md` 的那一轮运行，命令见
[`docs/bench-guide.md`](bench-guide.md)。

被测对象：`examples/knowledge-dba`（14 篇 / 40 片 @chunk=512,overlap=64，1024 维离线哈希嵌入），
题库 `eval/questions-dba.md`（44 题，top-5，多来源标注）。

---

## 1. 五条结论

1. **切片尺寸是唯一影响命中率的旋钮。** chunk=256 与 512 全部 97.7%，chunk=1024 全部 95.5%。
   1024 那档把 40 片压成 24 片，一个 chunk 塞进两三件事，证据被稀释——丢的是两道题：
   "一半 / 50%"那道词形题，加上 `VACUUM FULL 有什么风险`（期望 `pg-bloat`）。
   前者调参救不回来，后者是切片问题。
2. **维度是纯粹的压缩折衷，代价可量化。** 同一份语料，1024d → 97.7%，512d → 95.5%，
   256d → 88.6%，128d → 81.8%；存储 372 KB → 260 KB → 191 KB → 141 KB。
   要省 45% 体积，付 7 个百分点命中率，这个交换是可以写进配置说明的。
3. **IDF 与 overlap 在这套语料上已经不产生收益。** 同一切片尺寸下，idf on/off 的 hit@5 完全一致；
   MRR 上 off 反而**不低**于 on（chunk=1024 差 0.034–0.045，约等于两道题从 rank 1 掉到 rank 2；
   chunk=512 差 0.006，可忽略）。overlap 0/64/128 同理，只买到更多重复片。
   这不否定 IDF 的历史作用——早期 27 片 / 16 题的语料上它修好过排序——而是说
   **这份量尺已经量不出它了**。结论按语料规模写，不按记忆写。
4. **JSON 存储的检索是纯 CPU、零磁盘 I/O。** 440 次查询耗 1332 ms，CPU 占 wall 的 99.7%，
   `read_bytes` 为 0；全部向量常驻内存（40 片 × 1024 维，进程峰值 RSS 47.5 MB）。
   换句话说：查询端没有 IO 可优化，能优化的只有片数——而片数由切片尺寸决定
   （61 片 4.06 ms vs 24 片 2.05 ms，p50）。
5. **七层护栏 44/44、七层检查 18/18（另 1 项需库）全过，但测出了一个真 bug**，
   见第 4 节。逐层用例的价值就在这里：它问的不是"总的对不对"，而是"这一层对不对、理由对不对"。

## 2. 向量化：数字与读法

| 观察 | 数据 | 读法 |
|---|---|---|
| 切片尺寸 | 256/512 → 97.7%；1024 → 95.5% | 主因是证据被稀释，不是检索算法 |
| 片数 vs 延迟 | 61 片 4.06 ms；40 片 2.75 ms；24 片 2.05 ms（p50） | 线性于片数：JSON 存储是全量扫描 |
| 片数 vs 体积 | 487 KB；372 KB；272 KB | 片少总体积小，单片体积反而大（向量是固定开销） |
| 嵌入吞吐 | 850–2700 片/秒，0.37–1.33 ms/片 | 离线哈希的成本可以忽略，瓶颈永远在别处 |
| 维度 | 1024→512→256→128 各掉 2.2 / 4.9 / 11.9 个百分点 | 低于 512 维开始明显伤召回，不建议再压 |
| overlap | 0/64/128 差异 < 0.5 个百分点，但片数涨 5–9 片 | 只买到重复，没买到命中率，代价是延迟 |
| IDF | hit@5 无差异；MRR 上 off ≥ on（1024 档差 0.034–0.045，512 档 0.006） | 在这套语料上保留即可，别再拿它当卖点 |

**唯一稳定的失效样本**是同一个问题：`磁盘还有一半空间，为什么还要提前扩容？`
期望 `pg-capacity-planning`，实际拿到 `pg-spinlock-old-snapshot` / `pg-index-not-used` / `pg-upgrade`。
语料里写的是"50% 用量"，问句用的是"一半"——离线哈希词袋只看字面重合，同义不同词直接落榜。
它在 18 种配置里全部失败，**说明这是嵌入方式的问题，不是切片参数的问题**：
调参救不回来，换语义嵌入才行。这条比命中率本身更值得记住，因为它是"什么时候该换方案"的判据。

## 3. 存储对比：JSON 侧已测，pgvector 侧待跑

已测（JSON，40 片，44 题 × 10 轮）：

- 灌库 105 ms（含切片、建 IDF、嵌入、落盘），文件 372 KB
- 冷启动 20 ms，`read_bytes` 381 KB ——整个 store 一次性读进内存
- 检索 p50 2.645 ms / p95 3.268 ms / max 6.164 ms，CPU 99.7%，磁盘 I/O 为 0
- 峰值 RSS 47.5 MB（进程含 Python 运行时、嵌入、向量）

未测：pgvector 侧。本机没有运行中的 PostgreSQL 与 `psycopg`，所以报表第 3 节里
pg 一行是空的，并直接给出命令——**没有推测性数字**。在 VM 上跑完那一条之后，
这份文件要补的是三件事：

1. **灌库代价**：`PgStore.replace()` 是 autocommit 上逐行 INSERT，预期比 JSON 慢一到两个数量级。
   这是当前实现的真实行为，不是基准脚本的选择；如果数字难看，该改的是实现（COPY 或批量 INSERT），
   不是测量方式。
2. **检索延迟与索引的作用**：脚本会同时测 HNSW 与关掉 indexscan 的顺序扫描，
   两者比值就是"索引值不值"的答案。
3. **HNSW 是近似的**：脚本会报 top-1 一致率与 overlap@k。小语料上预期一致率很高；
   如果不高，说明 ef_search 需要调，而不是说明结果错了。

内存对比要分两个进程跑（`--backend json` 与 `--backend pg` 各一次），
同一进程里先跑一个再跑另一个，峰值 RSS 不可比。

## 4. 七层：结果与两个发现

**运行时护栏（guard.py）44/44 通过**，逐层都有正例与反例，并且断言的是"停在哪一层"和"理由是什么"，
不只是"拒绝了没有"：

| 层 | 覆盖 |
|---|---|
| L1 | 空串、纯空白、纯注释、`;` 拼接两条语句；带尾分号的单语句放行 |
| L2 | DROP/UPDATE 前缀被拒；`FOR UPDATE / FOR NO KEY UPDATE / FOR SHARE / FOR KEY SHARE` 四种行锁子句被拒；WITH / TABLE / VALUES / EXPLAIN 放行 |
| L3 | 藏在 CTE 里的 UPDATE / DELETE / CREATE；`SELECT … INTO`；注释里的 TRUNCATE 与字符串字面量里的 DELETE **不算** |
| L4 | pg_sleep / pg_read_file / nextval / pg_terminate_backend / set_config / pg_advisory_lock 全拒；无害的 `pg_size_pretty` 放行 |
| L5 | 白名单内放行；白名单外、未限定名的表、JOIN 夹带的第二张表全拒；不配白名单即该层关闭 |
| L6 | 无 LIMIT 补 `LIMIT 100`、随 `--max-rows` 变、已有 LIMIT 不动、**字面量里的 `'limit 3'` 不算 LIMIT**、小写 limit 识别 |
| L7 | 三条会话加固语句（`default_transaction_read_only` / `statement_timeout` / `idle_in_transaction_session_timeout`，超时值随 `--timeout-ms` 逻辑传入，用例用 2500ms 验证透传）、allow/block 各自的审计字段、每次工具调用落 `agent_trace.jsonl`、工具与 guard 共用同一道门 |

**静态检查（checks.py）18/18 通过**，同样正反成对：近名表/近名列、可空外键与可空键、
浮点金额、文本时间戳、无时区时间戳、集合表的可空键、无注释表、无列注释、时间命名不一致——
每一项都有"该报"和"不该报"两个用例，还有一个用例专门证明 check 5 不会从静态 DDL 里被伪造出来。

### 发现一：被拦下的写操作，审计日志里记成了 `ok`（已修）

L7-4 / L7-5 两个用例同时失败，指向同一处：`Toolbox.call()` 把 guard 的裁决留在了
handler 返回的 dict 里（`blocked` / `layer`），没有回填到 `ToolResult`。
后果是三个：

- `agent_trace.jsonl` 里，一次被拦下的 `DROP TABLE` 记为 `decision: "ok"`、`layer: ""`——
  这份日志存在的唯一目的就是记录"哪一层在什么时候拦住了什么"，字段却是空的；
- `ToolResult.brief()` 打的是 `not run: <reason>`，而不是 `BLOCKED at L2: <reason>`，
  模型看到的措辞比实际发生的事要模糊；
- 于是"你怎么知道它老实了"这个问题，靠日志答不上来。

修复：`call()` 在 handler 返回 `blocked` 时回填 `decision="blocked"` 与 `layer`。
同时把它加进了 `run_tool_selftest()`（第 7 例），所以 `demo.py` 会持续守住这个行为。
这是本轮测试最有价值的一条：**它不在任何单测的覆盖面上，因为单测直接调 `guard()`，
而线上路径走的是 `Toolbox.call()`。**

### 发现二：`current_setting` 被误杀（保留，但要知道）

L4-7：`SELECT current_setting('search_path')` 是只读的，却和 `set_config` 一起上了黑名单。
这是保守设计的副作用。它属于**有意留下的假阳性**：宁可让"读会话参数"这类只读请求被拒，
也不放行一个能改会话状态的家族。用例里标了 `known_false_positive`，
要改就必须连带改理由文案，别只删一个词。

## 5. 这轮测试自身的局限

- **量尺只有 44 题、14 篇**：hit@5 在 256/512 两档已经完全饱和（97.7% 上限被一题词形问题锁住），
  所以"IDF 与 overlap 无差异"这个结论的适用范围就是这个小语料，不代表大语料上也一样。
- **只测了离线嵌入**：API 向量模型的数字要 key，命令已给出但本轮未执行。
- **单机、单次**：每配置 3 轮查询、每题重复，够看量级，不够做显著性判断；
  报表里的差异小于 1 个百分点的一律按噪声处理。
- **Windows 计数器是好坏参半的**：RSS 与进程 I/O 可用（走 psapi/kernel32），
  但网络 I/O 不计入 `read_bytes`，所以 API 嵌入的耗时不能从 I/O 解释。
- **pgvector 与 HNSW 未测**：见第 3 节，命令已备好。
