# 容量评估：把增长曲线变成扩容触发条件

## 三个维度分开算

- **容量**：数据量、表与索引大小、WAL 生成速率
- **并发**：连接数峰值、QPS、事务数
- **资源**：CPU 使用率、IOPS / 吞吐、内存命中率

只盯磁盘容量是最常见的疏漏——磁盘还有 50%，但 IOPS 已经打满，
业务早就慢了，而监控面板上一切"正常"。

## 增长模型怎么建

按周采集，不要只看当前值：

```sql
SELECT pg_size_pretty(pg_database_size(current_database()));

SELECT schemaname, relname, pg_size_pretty(pg_total_relation_size(relid)) AS total
  FROM pg_stat_user_tables ORDER BY pg_total_relation_size(relid) DESC LIMIT 20;
```

再用 `pg_stat_statements` 的写入次数、`n_tup_ins` 的增长，估算行数增速。
注意留出膨胀系数：索引、死元组、以及临时文件，
实际占用通常是"裸数据量 × 1.5～2.0"。

## 一个合成换算示例

某物流轨迹库（虚构）：日均写入 2000 万行，行均约 300 字节。

- 日增裸数据：2000 万 × 300B ≈ 6GB
- 含索引与膨胀系数 1.8：约 11GB/天
- 保留 180 天：约 2TB，再按副本数与 30% 余量规划磁盘

同时估算 WAL：批量写入期间 WAL 生成速率可能达到平时的 3–5 倍，
归档盘和 `max_wal_size` 都要按峰值留量。

## 把触发条件写进监控

容量规划的输出不是一张 PPT，而是一组告警规则：

| 指标 | 告警 | 紧急 |
|---|---|---|
| 数据盘使用率 | 70% | 85% |
| WAL 归档盘使用率 | 60% | 80% |
| 连接数 / 上限 | 70% | 85% |
| 复制延迟（replay_lag） | 5s | 30s |

阈值要结合"从触发到扩容需要多久"来定。如果采购加扩容要两周，
那 85% 才告警就已经太晚了。

## 容量评审的节奏

- 月度：出一份容量报告，给出增长趋势和预测耗尽时间
- 大促/大版本上线前：按峰值做一次压测，验证模型而不是相信模型
- 决策留痕：每次扩容写清依据、预测值和实际值，一年后回顾偏差

好的容量管理不是"预测得准"，而是**在容量真正成为故障之前，
已经提前两周拿到了明确的、可执行的扩容建议**。
