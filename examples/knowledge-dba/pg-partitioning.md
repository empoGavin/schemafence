# 分区表：什么时候切、切多细、怎么维护

## 什么场景才值得分区

- 单表超过数亿行，且查询总是带时间范围（日志、订单、轨迹类数据）
- 需要按时间归档，希望"删历史"变成 `DETACH` 而不是 `DELETE`
- 单表索引已经大到维护窗口不够用

反过来说：**如果查询不带分区键，分区不会带来任何收益**，
反而让规划时间变长、跨分区查询变慢。先确认访问模式，再决定分区。

## 声明式分区与分区裁剪

```sql
CREATE TABLE events (id bigserial, tenant_id int, created_at timestamptz, payload jsonb)
  PARTITION BY RANGE (created_at);
CREATE TABLE events_2026_10 PARTITION OF events
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
```

裁剪生效的前提是谓词能被静态推导。两个常见失效场景：

- 查询写成 `WHERE date_trunc('month', created_at) = ...`，函数包住分区键
- 使用预编译语句走通用计划，参数值未知导致无法裁剪

用 `EXPLAIN` 确认计划里只出现目标分区，是上线前必做的一步。

## 分区粒度怎么选

- 按月：适合数据量大但查询跨度较长的场景，分区数可控
- 按天：适合写入量大、需要快速归档的场景，但要注意分区数量膨胀
- 一般建议单表分区数控制在几百个以内，再多规划开销会明显上升

## 维护动作要固化下来

1. **提前建分区**：至少提前 3 个月创建，用脚本自动建，别靠人记得
2. **归档**：`DETACH PARTITION` 后导出，比逐行删除快几个数量级
3. **统计信息**：分区表的 ANALYZE 按分区走，新分区建好后主动分析一次
4. **索引**：在父表建索引会级联到所有分区；单独建要小心遗漏

## 几个容易踩的坑

- 分区表上的唯一约束必须包含分区键，否则无法建
- 外键引用分区表、或分区表引用其他表，在旧版本支持有限
- 修改分区键不受支持，需要重建
- `DETACH` 时注意锁级别，CONCURRENTLY 变体在较新版本才提供

## 迁移路径：新分区表 + 增量同步 + 短暂切换

生产表改成分区表不能原地做。稳妥路径是：

1. 建新分区表，按历史范围预建分区
2. 用逻辑复制或双写把增量同步过去，历史数据分批导入
3. 校验行数与校验和
4. 在低峰窗口做秒级切换（改表名或改连接指向）

双写期间的冲突处理和数据一致性校验，是这个方案最花时间的地方，
必须提前设计好对账手段，不要指望切换当天再想办法。
