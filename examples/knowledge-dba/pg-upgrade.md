# 大版本升级：窗口估算、验证清单与回滚预案

## 三条路怎么选

- **pg_upgrade --link**：链路快，几乎不复制数据，但要求新旧目录在同一文件系统，
  切回旧版本很困难
- **pg_upgrade（默认复制模式）**：保留旧目录，可回滚，代价是停机时间随数据量增长
- **逻辑复制**：可跨大版本、可灰度、回退相对容易，但需要处理序列、
  DDL 变更和全量初始化时间

小库用 dump/restore 反而最省事；大库通常选 pg_upgrade，要求可回退就用复制模式。

## 停机窗口怎么估

`pg_upgrade --check` 先做预检，看兼容性问题。窗口估算至少包含：

1. 停业务 + checkpoint
2. pg_upgrade 本身耗时（复制模式正比于数据量）
3. 统计信息重新生成的时间——**统计信息不会被继承**，
   升级后必须重新 ANALYZE，否则上线初期计划会大面积抖动
4. 验证与回滚预留时间，通常再留 30%

## 必查清单

- **扩展兼容**：pgvector、pg_stat_statements 等是否支持新版本，需要重新编译或升级包
- **字符集与排序规则**：新版 glibc 的 collation 变更会影响索引顺序，需重建索引
- **默认参数变更**：新版本可能调整默认值（如并行度、检查点相关参数）
- **废弃特性**：`recovery.conf` 一类配置在新版本已移除
- **应用侧**：驱动版本、SQL 语法兼容、ORM 生成语句的差异

## 回滚预案

- 复制模式保留 `--old-datadir`，回滚就是切回旧目录启动
- 回滚窗口有限：一旦新库开始写入，回滚就会丢数据，
  所以"决策点"要提前定义（例如：上线 2 小时内出现 P1 问题就回滚）
- 回滚演练和升级演练同等重要，只演练升级不演练回滚是不完整的

## 升级后第一周的观察项

1. 慢查询排行变化——新版本 planner 可能改变计划
2. 连接数与内存占用——新版默认参数可能更激进
3. 复制延迟与 WAL 生成速率
4. 备份归档是否正常（配置项常被遗漏）

升级不是一次动作，而是一段观察期。把第一周定位成"密集观察 + 快速修正"，
比事后追查性能回归要省力得多。
