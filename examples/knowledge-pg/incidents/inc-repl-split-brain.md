# 切换后的脑裂：旧主没隔离又回来，两个主库各自写数据

## 现象

某订单库 `orders_prod`（虚构）在一次夜间网络抖动中触发了切换。主库 `pg-primary-01` 短暂不可达，运维判定其故障，把备库 `pg-standby-a` 用 `pg_promote()` 提升为新主，应用连接也切了过去，业务恢复。约 40 分钟后，`pg-primary-01` 网络自愈，**它以主库身份重新对外服务**——它从没被关停或隔离，一个残留在应用侧的老连接串、加上一个没更新配置的健康检查脚本，让它重新接受了一批写入。

于是出现最坏的局面：集群里同时存在两个都能写的 PostgreSQL 实例，各自在新老时间线上产生 WAL。这就是脑裂（split-brain），它的后续代价远高于当初那次网络抖动本身。

## 先收集什么证据

先回答一个问题：**到底谁是新主**。每个节点上都要问：

```sql
SELECT pg_is_in_recovery(),
       pg_current_wal_lsn(),
       (SELECT timeline_id FROM pg_control_checkpoint()) AS timeline;
```

再看每个节点的控制文件与时间线历史：

```bash
pg_controldata /var/lib/postgresql/16/data | grep -i "TimeLineID\|Latest checkpoint"
ls /var/lib/postgresql/16/data/pg_wal/*.history
```

主库视角看现在谁在复制谁：

```sql
SELECT application_name, client_addr, state, sync_state, sent_lsn, replay_lsn
  FROM pg_stat_replication;
```

应用与网络侧要单独取证：VIP / 域名当前指向谁、有哪些老连接串还在指向旧主、监控脚本对 "主库" 的判定依据是什么。

## 定位过程

第一步，用 `pg_is_in_recovery()` 定性。新主 `pg-standby-a` 返回 `false`（已不在恢复、可写），这符合预期；问题在于旧主 `pg-primary-01` **也返回 `false`**。两个节点同时"不在恢复"且都在接受写入，这就确认了脑裂。这一步不能只看连接或 VIP，必须逐个节点直连查。

第二步，看时间线判断分叉发生在哪。`pg_promote()` 在提升备库时会把它的时间线号推进一格——本例中新主从 timeline 1 变成 timeline 2，并在 `pg_wal` 里生成 `00000002.history` 这个时间线历史文件，记录"从某个 LSN 起，时间线 2 与时间线 1 分道扬镳"。`pg_controldata` 显示旧主仍停在 timeline 1。**时间线不同，就是分叉的硬证据**：同一个 LSN 之后，两个节点记录了互不相同的一组修改。

第三步，用 `pg_stat_replication` 看复制关系是否还存在：旧主的 WAL sender 列表是空的——它不是一个"被别人复制的备库"，它自己就是主库；新主那边也看不到旧主在流复制。两个孤立的写节点，各自向前。

**这里有两个反直觉的点必须讲清。** 其一：很多人认为"网络恢复了，让旧主自动重新连上、继续复制就好"。**这个判断是错的**。只要旧主在接受写入，它就已经和新主分叉，复制协议无法把分叉的备库"拉回来"继续流式跟随——那条路径只适用于"备库从未写入、只是落后"的情况。旧主必须通过 `pg_rewind` 或重做基础备份重新构建，才能作为新主的备库重新加入，它自己产生的那部分写入无法自动合并。其二：错的不是 `pg_promote()` 本身，**`pg_promote()` 只是让备库退出恢复、推进时间线**——它做得没错。错在切换流程**缺少了"隔离旧主"（fencing）这一步**，顺序是反的：应该是"先确保旧主不可能再被写入"，再提升备库，而不是反过来。文档里把这叫 STONITH（"爆头"），目的就是避免两个节点都自认为是主。

数据分叉之后，**只能选一边，不能合并**。原因很直接：同一个主键（例如订单号）可能在新老两边的同一时间段被改成了不同的值，自动合并无法判断哪个才是对的。所以处置必须明确"谁权威、谁的数据作废"。本例以"应用已经切到新主、新主承载了这段时间的正常业务"为依据，选择新主为准，旧主上那批写入按丢失处理并逐条评估是否人工补录。

## 结论与处置

根因：切换流程没有先隔离旧主，`pg-primary-01` 未被 fencing 便恢复服务并接受了写入，导致新旧主各写一条时间线、数据分叉。

处置动作：

- 立即隔离旧主：下线、屏蔽 5432、或防火墙封死，确保它不可能再接受任何写入。
- 冻结局面：暂停两边写入，先止损，再谈恢复。
- 确定权威节点：以新主为准（依据是应用已切换、业务数据在新主上持续产生）。
- 评估分叉窗口：从旧主 timeline 1 的 `pg_current_wal_lsn` 与切换点 LSN 之间，找出旧主分叉期内的写入，逐条评估丢弃或人工补偿。
- 旧主重新加入：用 `pg_rewind`（在时间线分叉但 WAL 仍可取得增量时，能省掉整份备份）或直接 `pg_basebackup` 重建，作为新主的备库；重建前务必确认它不再有任何写入。
- 清理隐患：更新或删除所有指向旧主的老连接串、修正监控脚本对"主库"的判定，把 VIP / 域名收敛到单一权威节点。

验证指标：全集群只有一个节点 `pg_is_in_recovery() = false`；所有备库 `pg_controldata` 的 timeline 与新主一致；`pg_stat_replication` 里旧主以 `state = streaming` 的身份重新出现；关键表在新主与重建后的备库上行数、校验和一致。

## 复盘要点

- **切换的第一步不是 `promote`，是隔离旧主**。fencing 先于提升，顺序错一次就可能是一次脑裂。
- **`pg_promote()` 与时间线的关系要记牢**：提升会让新主推进 timeline、生成 `.history`；timeline 不同即分叉。文档默认 `recovery_target_timeline = latest`，正是为了让正常备库自动跟随时间线变化。
- **脑裂后只能选一边**。同一主键两边被改成不同值，合并语义不确定，人工"两边都保留"往往是二次事故。
- **分叉的旧主不能靠"重新连上"复活**。它要么被 `pg_rewind` 拉回，要么整份基础备份重建。
- **演练必不可少**。切换流程的可信度只有一个来源——真正演练过一遍，包括应用侧连接切换和旧主隔离动作；把这些动作写进带顺序的检查清单，比事后补文档有效。
- **下次怎么提前发现**：监控"同时出现多个 `pg_is_in_recovery() = false` 的节点"这一异常组合，并对 VIP 归属做单一化校验；清理老连接串，堵住"旧主自愈后被误写"的入口。
