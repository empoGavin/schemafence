# 性能诊断流程（SQL 与执行计划）：瓶颈在第几步、为什么不对、怎么改

## 前提：确认这确实是"单条 SQL"的问题

从整库流程分岔进来时，应该已经拿到两个证据：`pg_stat_statements` 里少数语句占据了大部分累计执行时间，或者等待集中在少数语句触发的 `IO:DataFileRead` 上。**没有这两个证据就直接钻进执行计划，很容易在一个不是瓶颈的语句上优化半天。**

## 阶段 1：拿到可复现的 SQL 和它的参数

`pg_stat_statements` 里的 SQL 是**归一化的**——字面量被替换成 `$1`，所以直接拿去执行不会重现问题。

```sql
SELECT queryid, calls, round(total_exec_time::numeric,1) AS total_ms,
       round(mean_exec_time::numeric,1) AS mean_ms, rows, left(query,120)
  FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20;
```

拿到真实参数有三条路：从应用日志里取、从 `auto_explain` 采样的计划里取、或者用几个典型值逐个试。

**参数值决定计划**。同一个 SQL，传 1 个租户和传全部租户，计划器会给出完全不同的方案。所以复现时参数必须带上，否则你优化的可能是另一条语句。

## 阶段 2：跑一次带真实统计的执行计划

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, FORMAT TEXT)
SELECT ... ;
```

四个选项各自给什么：
- `ANALYZE`：真执行，拿到实际行数与时间——**没有它，你看到的只是估算**
- `BUFFERS`：每个节点读写多少块、命中多少——这是**判断"读得多"还是"读得慢"的唯一依据**
- `VERBOSE`：输出列与过滤条件
- `FORMAT TEXT` 便于人读；`FORMAT JSON` 便于程序解析

三条纪律：
1. **生产上谨慎执行**——`ANALYZE` 是真跑。用 `BEGIN; EXPLAIN ...; ROLLBACK;` 可以让写语句不落地，但对 SELECT 没有保护作用，该扫的页还是要扫。
2. **连跑两次**：第一次是冷缓存，第二次是热缓存。**两次的 `BUFFERS` 差值就是"这条语句到底读了多少盘"**。只跑一次会把缓存效应当成优化结果。
3. **记录当时的并发**：同一个计划在独占和满载下的实际耗时差别巨大。

## 阶段 3：定位瓶颈"在哪几步"

执行计划是一棵树，父节点的耗时包含全部子节点。所以**不能只看总耗时，要找"自身耗时"最大的节点**：

```
自身耗时 ≈ 本节点 total_time − 其所有子节点 total_time 之和
```

注意 `actual time` 与 `actual rows` 都是**每个循环的平均值**，真实量是 `× loops`。一个 `loops=10000` 的节点即使单次 0.01ms，累计也是 100ms。

判读顺序（这个顺序能过滤掉大部分噪声）：

1. **找 total time 最大的那个节点** —— 它是主要成本所在。
2. **看它的子节点是否已经解释了大部分时间** —— 如果解释了，继续往下钻；如果没解释（自身耗时占大头），它**就是瓶颈步骤**。
3. **对比 `rows`（估算）与 `actual rows`（实际）** —— 相差一个数量级以上，说明**根因是估算错误**，而不是执行方式本身错误。这是最容易走错的一步：看到 `Seq Scan` 就去加索引，而真正的问题是统计过期。
4. **看 `BUFFERS` 的 `read` 与 `hit` 比例** —— `read` 高说明真在读盘；全 `hit` 还慢，瓶颈在 CPU 或锁。

四类瓶颈节点的典型形态：

| 节点 | 形态 | 指向 |
|---|---|---|
| `Seq Scan` 且 `rows removed by filter` 很大 | 扫了很多、留下很少 | 访问路径不对或统计不准 |
| `Nested Loop` 且 `loops` 极大 | 内层被反复执行成千上万次 | join 方式不对 |
| `Sort` / `Hash` 且出现 `disk` | `Sort Method: external merge` | `work_mem` 不足或中间结果过大 |
| `Hash Join` 落盘、`Rows Removed by Join Filter` 大 | 连接产生了大量无用中间行 | 连接条件或顺序问题 |

## 阶段 4：把原因归到五类——"不对"到底不对在哪

### 类 1：表的访问路径不对（该走索引却顺序扫描）
先排除四种"索引用不上"的原因，再谈要不要加索引：

- **统计信息过期**：`pg_class.reltuples` 与实际行数严重不符，计划器以为表很小。判别：`EXPLAIN` 的估算行数与实际差一个量级。处置：`ANALYZE 表名`。
- **条件被表达式包裹**：`WHERE date_trunc('day', created_at) = ...` 或列上有隐式类型转换，索引列不可直接用。处置：改写为范围条件，或建表达式索引。
- **索引与操作符不匹配**：`LIKE '%x%'` 走不了 B-tree；数组/JSONB 需要 GIN。处置：换索引类型。
- **选择性太差**：条件命中了大半张表，计划器认为顺序扫描更便宜——**这不是错误，是正确判断**。处置：改条件是业务问题，不是数据库问题；或考虑分区。

### 类 2：JOIN 方式不对
三种 join 的适用面完全不同：

- **Nested Loop**：适合左表行数少、右表能用索引快速定位。**一旦 `loops` 上万且内层是顺序扫描，代价会爆炸。**
- **Hash Join**：适合两边都大、等值连接。代价是需要建哈希表；`work_mem` 不够会落盘。
- **Merge Join**：适合两边已按连接键有序，或大表间的等值连接。

**"join 方式不对"几乎总是上游错误的后果**，要顺着往下追：
1. 左表行数估算是否偏小 → 统计问题，导致计划器低估了 nested loop 的循环次数
2. 内层连接键有没有索引 → 没有索引的 nested loop 是最坏组合
3. `work_mem` 是否够建哈希表 → 不够时计划器可能退而选择更差的方案，或选中的 hash join 落盘

处置：先修统计，再补连接列索引，最后才调 `work_mem`（要按并发数算总内存，见进程与内存架构篇目）。

### 类 3：JOIN 顺序不对
`FROM a, b, c WHERE ...` 的显式连接、或者子查询折叠受限时（`join_collapse_limit`），计划器可能选了差的连接顺序。**判别方法是看中间节点的实际行数**：如果某一步产生了远超最终结果的行数，说明顺序让中间结果放大了。处置：重写为明确的 JOIN 层级，或把筛选性最强的条件提前。

### 类 4：排序与聚合代价
`ORDER BY` 无法由索引满足时必然产生 `Sort`。判读 `Sort Method`：
- `quicksort` / `top-N heapsort` → 在内存里，没问题
- **`external merge Disk: NkB` → 落盘**，需要抬 `work_mem`，或者用索引消除排序

### 类 5：并行度不合适
`Gather` / `Gather Merge` 节点下是并行 worker。并行不是越多越好：**并行 worker 会争抢 CPU 和 IO，在已经饱和的机器上并行反而更慢**。判别：单条语句变快但整体 QPS 下降，就是并行过度的信号。

## 阶段 5：验证——必须用可比的量

优化做完，用同样的参数、同样的缓存状态再跑一次，比对四个量：

1. **`actual time` 总量**（不是单节点，是树根）
2. **`BUFFERS` 的 `read` 总数** —— 这个最能说明"是不是少读了"
3. **`rows` 估算与实际行数的偏差是否收敛** —— 说明统计是否修好
4. **瓶颈节点是否已经换人** —— 优化常会把瓶颈推到下一段，此时要决定是否继续

**只报"变快了"不算验证**。要报的是"读块数从 84 万降到 1.2 万，耗时从 12s 降到 180ms，估算偏差从 500 倍收敛到 1.3 倍"。

**怎么证明优化真的有效**：唯一站得住的做法是**用改动前的同一组量化指标做前后对比**——同样的参数、同样的缓存状态、同样的并发水平，比较 `actual time` 总量、读块数（`BUFFERS` 的 `read`）、估算偏差是否收敛，以及瓶颈节点是否转移。**"感觉快了"不是证据**：缓存变热、并发下降、统计刚被 ANALYZE 过，都会让同一条 SQL 显得更快，而这些变化与你的改动无关。

## 阶段 6：把结论写回知识库

每条 SQL 优化都是一次可复用的判断。留下四样东西：SQL 原文与参数、优化前后的执行计划、关键指标对比、以及**一句话的根因归类（属于上面五类的哪一类）**。

**归类这一步决定了经验能不能迁移**：写下"这条 SQL 慢了"，三个月后没人知道能不能套用到别的语句；写下"类 2：join 方式不对，根因是连接列无索引导致 nested loop 循环 8 万次"，下次遇到类似形态可以直接对上。
