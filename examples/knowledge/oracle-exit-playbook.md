# 去 O 项目方法论（抽象版）

## 阶段划分

去 O 不是"把 Oracle 换成 PostgreSQL"，而是三个可以独立验收的动作：

1. **验证方向**：选一到两个非核心系统做兼容性验证，明确哪些语法、哪些特性是硬依赖
2. **总体方案**：确定目标数据库、分工（哪些应用改代码、哪些靠兼容层）、切换单位（按产品还是按 Region）
3. **切换方案**：每个切换单元的停机窗口、回滚条件、数据校验方式、负责人

## 三个决定成败的设计

- **双跑与对比**：切换前让新旧两套并行写入，逐日比对结果集。不比对就切换，等于赌
- **按 Region 灰度**：先切流量最小的区域，用真实流量验证，再逐区放大。全球 20 个 Region 顺序推进，
  每切一个都留出观察期
- **回滚预案必须演练过**：写在文档里的回滚步骤，没演练过的等于没有

## 零停机切换的技术要点

零停机不是"不中断"，而是"中断窗口小于业务可感知阈值"。常用的手法：

- 全量迁移 + 增量追平（逻辑复制或触发器日志）
- 切换瞬间只读几秒，校验行数与关键指标后再放量
- 应用连接串通过配置中心切换，不重启进程

## 最容易低估的部分

技术方案通常不是瓶颈，瓶颈在**验收标准**：什么叫"切换成功"？
必须提前定义可量化的判据——错误率、关键接口的 P99、数据一致性的抽样比例。
没有判据的项目，切换之后会陷入无休止的"感觉有点慢"的争论里。

## 与 AI 的结合点

去 O 沉淀下来的最大资产不是代码，是**差异清单**：
Oracle 与 PostgreSQL 在语义上的每一处不同。这份清单正好是 AI 生成 SQL 最容易踩错的地方——
把差异清单做成机器可读的约束，就是我们这个项目在做的事。
